# GenIaC-SecBench Data Dictionary & File Guide

This document explains every output file generated by the GenIaC-SecBench pipeline, now organized in the `data/summary_reports/` directory. It details what tool generated the file, the data it contains, expected results, and explanations for known anomalies.

---

## 1. Raw Findings & Validation Data

### `findings_raw.csv`
- **Generated By:** `src/geniac_secbench/phase3_scanning/parse_results.py`
- **What it is:** The consolidated master list of every single vulnerability found by all three scanners (Checkov, Trivy, KICS) across all generated files.
- **Columns:** `scanner`, `rule_id`, `severity`, `description`, `status`, `dataset_type` (simple/complex), `model`, `scenario_id`, `cis_category`
- **Expected Results:** Tens of thousands of rows. 
- **⚠️ Known Anomaly (The "UNKNOWN" Severity):** You will notice many rows where `severity` is `UNKNOWN`. **This is exclusively caused by Checkov.** By default, the open-source CLI version of Checkov does not assign CVSS severity tiers (Critical, High, Medium, Low) to its standard rules unless connected to the paid Bridgecrew API. Trivy and KICS *do* provide severities natively. Therefore, all Checkov findings default to `UNKNOWN`. This is expected and normal for this tool.

### `schema_validity.csv`
- **Generated By:** `src/geniac_secbench/phase2_validation/validate_iac.py`
- **What it is:** Results of the syntactic and schema validation phase. Tests if the LLM hallucinated invalid cloud resources.
- **Tools used:** `terraform validate`, `cfn-lint`, `kubeconform`, and strict ARM JSON parsing.
- **Columns:** `dataset` (simple/complex), `model`, `scenario_id`, `tool` (e.g. Terraform), `is_valid` (True/False), `error_message`
- **Expected Results:** True for most models. Complex scenarios usually have lower validity rates than simple ones. **Invalid files are NOT skipped in Phase 3 scanning by default** -- `run_scanners.py` scans everything and relies on this column for downstream filtering (pass `--exclude-invalid` to opt into skipping at scan time instead; see `docs/THREATS_TO_VALIDITY.md` #5 for why this default was chosen).

### `resource_counts.csv`
- **Generated By:** `src/geniac_secbench/phase3_scanning/run_scanners.py` (specifically extracted via Checkov's AST parsing)
- **What it is:** The exact number of cloud resources instantiated in each scenario block.
- **Columns:** `dataset_type` (simple/complex), `model`, `scenario_id`, `resource_count`
- **Why it matters:** Raw vulnerability counts are meaningless because a script with 10 resources will naturally have more vulnerabilities than a script with 1 resource. This file provides the denominator for our primary metric: `vulns_per_resource`.

### `structural_metrics.csv`
- **Generated By:** `src/geniac_secbench/phase4_structural/extract_metrics.py`
- **What it is:** Deep Abstract Syntax Tree (AST) metrics used to prove that the models are actually generating complex code, not just basic stubs.
- **Columns:** `resource_count`, `resource_diversity`, `ast_depth`, `iam_complexity`, `dataset` (simple/complex), `model`, `scenario_id`, `file_name`

### `scan_coverage.csv`
- **Generated By:** `src/geniac_secbench/phase3_scanning/run_scanners.py`
- **What it is:** Per (dataset, model, scanner) row showing how many scenarios were scanned vs. how many exist. Added during the Aug 2026 remediation specifically so scanner coverage gaps are visible in an output file rather than discoverable only by cross-referencing raw JSON -- see `docs/THREATS_TO_VALIDITY.md` #1.
- **Columns:** `dataset`, `model`, `scanner`, `scenarios_total`, `scenarios_covered`
- **Expected Results:** `scenarios_covered == scenarios_total` for every row after a full `--phase scan` run. A short row means that (model, scanner) pair needs re-running.

## 2. Aggregated Summary CSVs

These files are aggregations created by `parse_results.py` to make charting easier.

### `summary_severity.csv`
- **What it is:** Vulnerability counts grouped by Model and Severity.
- **Note:** As explained above, the massive `UNKNOWN` counts (e.g., 1700 for Opus 4.6, 1313 for Gemini 3.1 Pro) represent all the findings from Checkov. The Critical/High/Medium/Low counts come from Trivy and KICS.

### `summary_vulns_per_resource.csv`
- **What it is:** The most important security metric in the paper. Computes `(total vulnerabilities from all scanners) / (resource count)` for each scenario.
- **Expected Results:** Lower is better. A score of `0.5` means 1 vulnerability for every 2 resources provisioned. This normalizes the data so large complex scripts can be fairly compared against small simple ones.

### `summary_model_scanner.csv`
- **What it is:** Shows how many vulnerabilities each individual scanner (Checkov, Trivy, KICS) found per model.
- **Expected Results:** Checkov typically finds the most vulnerabilities because it has the broadest set of IaC rules, followed by Trivy, then KICS. 

### `summary_cis_category.csv`
- **What it is:** Vulnerabilities mapped into 6 human-readable categories based on CIS (Center for Internet Security) benchmarks: `IAM`, `Encryption`, `Network`, `Logging`, `Compute`, `Storage`.
- **Expected Results:** Used to generate the Heatmap figure. Shows you *where* models are weak (e.g., failing to encrypt S3 buckets vs leaving SSH open).

### `summary_pass_rate.csv`
- **What it is:** The percentage of scenarios that passed Phase 2 validation (no syntax errors or hallucinated resources) per model.

## 3. Statistical Analysis JSONs

These files contain the rigorous math proving the benchmark results.

### `master_results.csv`
- **Generated By:** `src/geniac_secbench/phase6_statistics/build_master_table.py`
- **What it is:** The "God Table". Combines Phase 2 (validity), Phase 3 (vulns per scanner), and Phase 4 (resource counts) into a single 922-row table. Every statistical test runs off this file.

### `statistical_results.json`
- **Generated By:** `src/geniac_secbench/phase6_statistics/friedman_test.py`
- **What it is:** The results of the non-parametric Friedman ANOVA and Wilcoxon post-hoc tests.
- **How to read:** 
  - `p_value` under the Friedman test tells you if the models differ overall (it should be very small, e.g., `< 0.05`).
  - `post_hoc` shows head-to-head comparisons (e.g., GPT-4o vs Claude 3.5 Sonnet) and tells you if one is statistically significantly better than the other.

### `nb_glmm_results.json`
- **Generated By:** `src/geniac_secbench/phase6_statistics/nb_glmm.py`
- **What it is:** The Negative Binomial Mixed-Effects Regression. It mathematically isolates the effect of "Complexity" while controlling for individual model quirks.

### `ks_test_results.json`
- **Generated By:** `src/geniac_secbench/phase4_structural/ks_test.py`
- **What it is:** The Kolmogorov–Smirnov test results comparing the structure of code across models. Proves mathematically if a model is "cheating" by generating unusually simple or degenerate code. (e.g., this file proves `phi3` is a massive structural outlier).
